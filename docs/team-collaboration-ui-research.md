# 团队化多 Agent 协作 · 界面逻辑研究

> 2026-11-10 研究快照。研究命题（来自产品方向）：**界面更方便、可视化更好；以本地文件为多节点共享知识；多 Claude agents 高效协作；方便观察协作过程；形同一个团队、一个公司，为同一目标不断前进、时刻不停。**
>
> 本文回答三件事：现有界面逻辑长什么样（§2）、离这个愿景差在哪（§3）、分阶段怎么补（§4）。是研究+提案，不是实施承诺——落地项需走 brainstorm → spec → plan 流程（`.claude/skills/dagents-patterns/`）。与既有路线的关系见 §5。
>
> **实施状态（2026-11-10 当日）**：方向 A/B/C/D 四个方向已全部落地 MVP 并通过测试与浏览器验收（网关 456+ 测试全绿、console 452 测试全绿；e2e 冒烟含 goal 自动推进/评估闭环、黑板端到端、UTF-8 回环）——入口 `/team` 公司作战室与 `/goals` 目标看板（导航「团队 / 目标」）；细节见 `AGENTS.md` 架构总览段与 `CHANGELOG.md`。设计优化 10 轮（信息层级/三态/色彩/密度/反馈/可访问性/响应式/一致性/动效/文案）已随实施完成。

## 0. 一句话判断

**单 run 的过程观察已经是一流水平**（摘要/终端/轨迹三视图 + 直播 SSE + 节点泳道甘特）；缺的是它上面的一层——**「公司层」**：

1. **看不见整个团队**：观察单位是「一次 run」，没有跨 run / 跨 agent 的聚合视图——打开任何一个页面都回答不了「我的公司此刻在干什么」；
2. **agent 之间没有共享记忆**：节点间知识只有 `{{id.output}}` 边传递（64KB 截断、DAG 单向、run 结束即蒸发），本地文件这个天然黑板没有被用作协作知识层；
3. **团队不会自己转**：run 全部由人触发、一次性终止，「为同一目标持续前进」缺少目标实体、任务分配与调度闭环。

好消息：三块地基都已在仓库里——`run-live-registry` 支持多路并发直播订阅、`RunTraceModel` 纯投影层天然可扩展成多 run 聚合、registry-not-database 哲学与 50 人格「公司组织架构」库正好承接文件黑板与虚拟公司叙事。

## 1. 愿景拆解：六项要求 → 产品语言

| # | 用户要求 | 产品语言 | 现状满足度 |
|---|---|---|---|
| 1 | 更加方便 | 团队运作的统一入口、低操作成本 | 中（Cmd+K / 模板 / 悬浮副驾在，但团队视角无入口） |
| 2 | 可视化更加好 | 过程可视化的信息密度与聚合度 | 单 run 强 / 跨 run 无 |
| 3 | 本地文件为多节点共享知识 | 文件系统黑板 = agent 间与跨节点知识真相源 | 弱（文件只作 cwd，不作知识层） |
| 4 | 多 Claude agents 高效协助 | 任务分解、并行、交接、互相可见 | 引擎层有（并行波次/子流程），知识层无 |
| 5 | 方便观察协作过程 | 跨 run 聚合的过程可观察性 | 弱（必须逐 run 进画布） |
| 6 | 团队/公司持续前进、时刻不停 | 目标驱动的持续运行（goal loop + 调度） | 无（run 一次性、人触发） |

## 2. 现状盘点：界面逻辑今天长什么样

### 2.1 信息架构（IA）

- `/` = **Flows 工作台**（Workflow-First，2026-09-06 定稿）：FirstRunReadiness 自检条 → 范围 tab → 工具栏（搜索 / 从模板创建 / 一句话生成 / 新建）→ flow 卡片列表（卡片带真实运行状态徽章，running 时 3s 轻轮询）；空态英雄区三入口；
- 主导航 `app-nav-sidebar` 5 个一级入口：工作流 / 智能体 / 技能 / 终端 / 守护进程（+ 页脚设置）；⌘K 命令面板居导航与会话树之间；
- Chat 是**全局悬浮副驾** `floating-chat`（自由拖动、位置记忆、@-命令菜单：@agent / @flow / @workflow / @daemon）；
- 模板与运行历史**有意不占导航位**（模板在工具栏、历史在 flow 卡片展开区 `FlowRunsPanel`）；**全局 /runs 页曾被裁决删除**——历史回到 flow 上下文（这条裁决对本研究的含义见 §3-D1）。

### 2.2 单 run 观察链（现状最强项）

- **画布运行态**：节点徽章（进行中旋转/完成绿/失败红）+ 连线点亮（完成段渐变/活动段流动）；
- **结果面板三视图** `canvas-results-panel.tsx`：摘要 / 终端 / 轨迹；
- **直播**：`GET /runs/:runId/live` SSE（hello.replay 前缀 + 实时帧，帧带服务端时间戳）；运行中可插话（`POST .../message`）；
- **轨迹视图** `canvas-trace-view.tsx`：节点泳道甘特（框选过滤/缩放/平移）+ 事件台账 + Inspector 覆盖层；`lib/run-trace-model.ts` 纯投影层让「直播帧」与「DB spans」两路数据产出同一模型；
- **运行历史** `FlowRunsPanel`：每 flow 卡片展开，含节点画像（analytics API）、续跑谱系（resumedFromRunId 缩进 + ↩）、8 种终态诚实展示（部分成功/预算停机/等待输入…）、失败行「终端」深链；
- **人在环路的交互词汇已建立**：awaiting_input 应答条（原地续跑）、失败断点「从此处继续（跳过 N 节点）」、运行中 stdin 插话、停止、重跑预填、`/terminal?agent=` 交互式 agent 会话——「人对执行出手」的手段齐全；
- **旁观模式**：`/workflows/:id/canvas?run=<runId>` 可旁观任意运行（含 chat @flow 触发的）；聊天里 `WorkflowRunCard` 收起态就是一条节点进度链（绿点/旋转/红点逐个点亮）——聊天内嵌的迷你团队视图。

> 结论：**「看一次 run」的体验闭环完整且细腻**。轨迹甘特的泳道模型（每节点一条 lane）已经是「多 agent 并行工作可视化」的原型——只是它的边界是单 run，且泳道单位是**节点 id**而非 **agent 身份**。

### 2.3 跨 run / 跨 agent 视角（现状最弱项）

- **没有全局运行视图**：`GET /runs?status=running` 后端存在（跨 flow 列运行中 run），但界面上没有页面消费它——想看「现在有几个 agent 在干活」只能逐 flow 卡片展开；flows 列表徽章是唯一的全局脉搏，且是 per-flow 最近一次状态；
- **Agents 页是资产页不是运作页**：列表 + 广场 + 详情（人格、技能、30 天活动 sparkline、负载估算条、实测成本、交互式会话入口）——展示「agent 是谁」，不展示「agent 正在干什么」；设计注释明确写着「no KPI row, no kanban; clean scannable list」——**团队观察面需要新的页面定位（观察台），不是往管理列表里塞 KPI**；
- **fleet-stats 富看板模型已写好但未挂载**：`lib/fleet-stats.ts` 有完整的 KPI 投影、任务密度瓦片图（「百万 agent 热力图」的 MVP 替身）、吞吐、按模型用量等纯函数（带单测），数据面 `GET /api/fleet-stats` → dispatch——但 Daemons 页只把整包投影成一个「活跃任务」数字；且它是 daemon/dispatch 视角，本机 inline CLI runs 不流经 dispatch，**本机团队聚合需要 runs + usage 数据源**（投影模式可复用）；
- **用量与成本**（Settings tab）已有按 Agent / 按 Flow 的实测聚合（7/30/90 天）——团队 KPI 的数据基础在，只是藏在设置里、纯回溯、无实时。

### 2.4 知识与上下文的现状

| 层 | 机制 | 性质 |
|---|---|---|
| 节点间 | `{{id.output}}` 模板引用 + 多入边合并（64KB 截断） | run 内、单向、字符串、易失 |
| flow 级 | `flows.context_md`（画布「上下文」面板编辑，「CLAUDE.md 的 flow 版」，131k 字符上限；运行时 8KB 预裁注入**每个** LLM/Agent 节点 system 前部；随版本快照/回滚） | 静态、人工维护 |
| 会话级 | chats 滚动摘要 + `includeChatHistory` 混合检索 | 单会话，DB 内 |
| 资产级 | 技能库 `~/.agents/skills`、人格库 `~/.agents/agent-library`（registry-not-database） | 文件真相源，但只装「静态资产」，不装运行时知识 |
| 项目级 | `directories` 表（id/path/name）→ 目录锚贯穿全链路（聊天发送/运行面板/终端 tab/失败深链）、CLI agent 在该目录 cwd 读写文件 | **只有路径语义，没有任何知识语义** |

> 关键事实：CLI agent（claude）在项目目录里本来就会读写文件——**文件协作能力天然存在，缺的是「约定 + 注入 + 观察」三层界面/引擎支持**。agent 改动文件在聊天里能看到 diff 卡（`file-diff-view`），但画布 run 里文件级产出不在观察面里。

### 2.5 「团队」概念的现状

- **人格库 = 公司组织架构**：`apps/gateway/builtin-library/` 13 个部门（engineering / product / design / marketing / research / testing / security / support / project-management / …）50 人格；
- **团队创建入口已产品化**：Agent 广场「团队场景」tab + 模板库「虚拟团队」tab——一键实例化（成员解析/缺失降级 LLM 节点的 UX 已打磨，`TeamTemplateSummary` 带 shape 队形与成员清单），落点是「建 flow + 启用成员 Agent → 跳画布」；
- 产品叙事已定稿为「**一个人指挥一个虚拟团队**（solo orchestration）」（product-review.md 张力 3 + 方案 F 已交付的改名）——与本愿景完全同向；
- 但今天「团队」= 一次性的 DAG 编排：模板实例化 → 跑一次 → 结束。团队没有持续存在感（无运行时花名册、无进行中的任务板、无按团队的用量聚合）。

### 2.6 持续运行的现状

- run 由人触发、跑完即止；引擎内循环原语（iteration `whileCondition`「循环直到 X」、`concurrency` 1-8、`executeFlow` 子流程深度 3）都是 **run 内部的**循环，没有跨 run 的连续性；
- 无 scheduler / 定时 / 事件驱动触发；无 goal/mission 实体（最接近的是 run 输入框里的一句话）；
- 护栏反而已备好：run 级 `tokenBudget`（越线停机）、CLI 并发闸（16）、run 并发闸（8）、看门狗——**持续运行缺的不是安全阀，是引擎与界面**。

## 3. 差距分析：六项要求逐条对照

### D1 团队鸟瞰缺失（对应要求 1/2/5）

观察的原子单位是 run，而用户心智的原子单位是「我的团队/公司」。要在现有界面回答「谁在干什么、进展如何」，用户需要：逐个 flow 展开 → 逐个 run 进画布 → 逐个切轨迹视图。信息没有聚合面。

两条既有界面裁决划定了补这块的姿势：

- **全局 /runs 页已删**（裁决：历史回到 flow 上下文）——团队观察面**不能是「恢复全局历史列表」**，它必须是实时聚合的作战室形态（历史仍按 flow 归属，作战室只做「此刻」+ 深链跳走）；
- **Agents 页注释明确拒绝 KPI 行/kanban**（定位是干净的可扫描管理列表）——团队观察面是**新页面**（观察台），不是给现有页面加塞。

另两个被调研确认的具体空缺：轨迹泳道按**节点 id** 分道而非 **agent 身份**（同一个人格跑多个节点时无法按「人」聚合）；协作事件的通知面只有 toast（无活动流/事件中心）。

### D2 运行时共享知识缺失（对应要求 3/4）

- 并行分支之间**无法互通**（DAG 边单向：fan-out 的三个 agent 互相看不到彼此产出，只有汇总节点能看到全部）；
- 大块结构化产出（调研报告、代码索引、决策记录）挤不进 `{{id.output}}` 的 64KB 合并管道；
- run 结束知识即蒸发——下一次 run 从零开始（除会话历史外无跨 run 记忆）；
- 「本地文件」这层用户明确点名的共享介质，目前只承载 cwd。

### D3 目标与持续性缺失（对应要求 6）

- 「为同一目标」没有实体：目标只活在每次 run 的输入字符串里；
- 「不断前进」没有机制：没有「评估上轮 → 生成下轮任务 → 继续跑」的循环，更没有界面呈现「目标 → 当前轮次 → 累计投入 → 距验收还差什么」；
- 「时刻不停」没有调度：夜间/无人时团队静止。

### D4 可视化密度与美的提升空间（对应要求 2）

- 轨迹甘特是全仓库最好的可视化资产，但被锁在单 run 结果面板里；
- 画布对「多次运行对比」「团队编制」没有表达；
- 文件知识的演化（谁写了什么、改了什么）完全不可见（diff 卡只在聊天里）。

## 4. 改进蓝图（提案）

> 四个方向按「复用现有资产的比例」排序，A/B 几乎纯组装，C 需要新引擎语义，D 锦上添花。

### 方向 A：公司作战室（Team Room）——跨 run 聚合观察 【P1，组装为主】

**一句话**：新页面（建议 `/team`，导航首位）把「此刻全公司 + 今日战报」放进一屏。**它不是恢复已删除的全局 runs 历史页**——历史仍按 flow 归属（FlowRunsPanel 不动），作战室只呈现「此刻 + 今日」并深链跳走（旁观 `?run=` / 终端 / 目标卡）。

**界面形态**（三层，从上到下）：

1. **KPI 条**：运行中 run 数 / 活跃 agent 数 / 今日完成·失败 / 今日成本·token（数据全现成：`GET /runs?status=running` + `usage/summary`）；
2. **公司活动墙**：所有 running run 的实时事件流合流成一条 feed（agent X 开始节点 Y / 产出 Z / 失败 W），每行可点击深链到画布旁观 `?run=`；来源 = 对每个 running run 各开一路 `run-live` SSE，`run-live-registry` 现支持 64 并发条目 + 多订阅者，**网关零改动或仅加一个聚合端点**；
3. **成员卡片行**：启用中 agents（人格头像/部门/最近活动摘要/当前是否在 run 中）——把 Agents 页的静态资产卡升级成「值班状态卡」。

**复用**：`RunTraceModel` 投影层（feed 行 = TraceRecord 的跨 run 版；泳道单位从节点 id 换算到 agent 身份——platformAgent 节点有 agentId，透视即可）、旁观深链、usage 聚合、agent sparkline；`lib/fleet-stats.ts` 那套「纯投影函数 + 单测」的看板建模模式（KPI/密度瓦片）可直接平移——注意其数据面是 dispatch 视角，本机团队聚合改用 runs + usage_events 数据源。
**新增**：聚合 SSE 端点（`GET /team/live`，可选：先由 console BFF 扇出多路 `run-live` 也是零网关方案）、Team Room 页面。
**为什么先做它**：它是其余方向的观察面——文件黑板（B）和目标环（C）都需要一块「公司级」的屏幕来呈现。

### 方向 B：文件黑板（File Blackboard）——本地文件共享知识 【P1-P2，哲学完全同构】

**一句话**：把 registry-not-database 从「静态资产」扩展到「运行时协作知识」：项目目录（或 `~/.agents/`）下约定一棵知识树，agents 读写它，界面观察它。

**约定（草案）**——项目目录下：

```
.agents/
  BOARD.md          # 任务板：目标、任务清单（谁认领、什么状态）—— kanban 的文件形态
  knowledge/        # 沉淀的知识条目（调研结论、决策记录、索引）—— 跨 run 复用
  handoff/          # 交接条目：fan-out 分支结束时各写一份，汇总节点/下一轮读取
```

**三层支撑**：

1. **注入层**（引擎）：复用 `flows.context_md` 的注入管线，扩出「目录级上下文」——run 的 `directoryId` 解析出 `.agents/` 摘要（BOARD + knowledge 目录清单）注入每个 Agent/LLM 节点 system 前部；并行分支写 handoff、汇总节点读 handoff，绕开 64KB 边管道；
2. **书写层**（自然能力）：CLI agent 在 cwd 写文件是本来就有的行为，只需要人格/模板里写明黑板纪律（「完成时更新 BOARD.md 你的任务行」「重要结论写 knowledge/ 一条」）——团队模板 `TeamStep.task` 指令正好是挂这种纪律的位置；
3. **观察层**（界面）：
   - 画布/Team Room 增加**黑板面板**：文件树 + markdown 渲染 + 变化时间线（谁在哪次 run 改了哪个文件——复用 `file-diff-view`）；轮询或 gateway fs.watch 皆可（MVP 轮询 5s 足够）；
   - BOARD.md 的任务行结构化渲染 = 免费 kanban 视图。

**多节点（多机）读法的承接**：文件是真相源 + git 同步 = 天然的多机共享方案——daemon 远程节点 clone 同一仓库即共享同一黑板，不需要中心 DB。这与「以本地文件为多节点共享知识」的多机语义严丝合缝，且与 §5 的 Non-Goals（不做多人协作 SaaS）不冲突。

**风险**：并发写冲突（MVP：BOARD 按任务行分区 + 约定「只改自己的行」；文件级原子写）；知识腐化（需要保留/归档策略，交给模板纪律与用户治理）。

**线框（黑板面板，挂在画布结果面板/Team Room 侧栏）**：

```
┌─ 黑板 · /project/.agents/ ────────────────────────┐
│ ▸ BOARD.md                          更新于 14:02  │
│   ├─ ✅ 竞品分析报告  产品调研员  14:01 完成      │
│   ├─ ◐ 落地页实现    前端工程师  进行中(6m)       │  ← 任务行结构化渲染
│   └─ ○ 回归验证      测试工程师  待认领            │
│ ▸ knowledge/（4）                                  │
│   ├─ 竞品对比矩阵.md   +14:01 产品调研员  [diff]   │  ← 变化时间线
│   └─ 技术选型决策.md   +13:47 架构师      [diff]   │
│ ▸ handoff/（2 · 本轮）                             │
└────────────────────────────────────────────────────┘
```

### 方向 C：目标环（Goal Loop）——为同一目标持续前进 【P2，需要新语义】

**一句话**：给「目标」一个实体和一台引擎：goal → 编排 flow → 跑 → 验收 → 生成下一轮 → 循环，直到验收通过或预算耗尽。

**数据模型**：`goals` 表（描述 / 验收标准 / 关联 flow 或模板 / 预算（复用 tokenBudget 语义的 goal 级累计）/ 状态 / 轮次游标）；每轮产出 `runs` 行（`goal_id` 外键），黑板 BOARD.md 承载轮间任务交接。

**引擎形态**（两个候选，倾向前者）：

- **C-1 宿主侧 supervisor**（gateway 内）：一个 goal loop 服务——验收用 LLM judge（outputSchema 校验 + 评估 prompt），下一轮任务生成走既有 `flow-generator` 管线；对引擎零侵入；
- C-2 引擎侧长 run：把 whileCondition/iteration 扩成跨 run 语义——侵入大、与「run 有终态」的既有语义（boot sweep、取消、预算）冲突，不建议。

**界面形态**：**目标看板**（OKR 视图）：每 goal 一张卡——目标 / 当前第 N 轮 / 状态（跑着/等人/等预算）/ 累计成本·token / 最近一轮产出摘要 / 验收差距；点进 = 该 goal 的 run 谱系时间线（复用轨迹甘特做跨 run 聚合投影）+ 黑板视图。「人」出现在环里的位置沿用 HumanInput（挂起等人），保持「人批准下一轮」的可选闸门。

**护栏（全部复用现有）**：goal 级预算（tokenBudget 语义上移累计）、CLI/run 并发闸、看门狗、`/metrics` 暴露 goal loop 水位；「时刻不停」默认带预算与静默时段，而不是字面意义的无限跑。

**线框（目标看板）**：

```
┌─ 目标 ────────────────────────────────────────────────────────┐
│ ◉ 旧官网重构            第 3 轮 · ◐ 跑着（前端工程师）           │
│   验收 4/6 项通过 · 累计 $3.12 / 预算 $10 · 本轮 14:01 起        │
│   ▸ 下一动作：等待「回归验证」节点完成 → 自动验收评估              │
│ ─────────────────────────────────────────────────────────────  │
│ ○ 周报自动生成          每周五 18:00 轮询 · 预算 $1/轮            │
│ ─────────────────────────────────────────────────────────────  │
│ ✓ API 文档补全          第 2 轮验收通过 · 已归档 · 共 $1.04       │
└────────────────────────────────────────────────────────────────┘
   点开目标 → run 谱系时间线（跨 run 轨迹甘特）+ 黑板 + 验收记录
```

### 方向 D：可视化增强（贯穿 A-C 的呈现层）【P2-P3】

- **公司时间线**：`RunTraceModel` 从单 run 泳道扩展为多 run 拼接泳道（x 轴真实时间、每 run·节点一条 lane）——轨迹甘特的所有交互（框选/缩放/Inspector）平移复用；
- **多次运行对比**：同一 flow 的 run 谱系在画布上叠加对比（节点耗时热力/成功率着色；analytics API 已有数据）；
- **黑板演化视图**：知识文件的时间线 + diff（复用 `file-diff-view`），回答「团队今天学到了什么」；
- **Team Room 的美感基线**：遵守现有 PX 状态点规范（dot-running/done/queued 家族），不新造视觉语言。

## 5. 与现有产品路线的关系

- **不冲突，且互补**：product-plan.md 方案 A-G 聚焦「单次执行的质量与诚实」（生成质量/可中断/成本实测/分级）；本蓝图聚焦其上的「组织层」。A（作战室）依赖的 usage 实测（方案 D 已交付）与运行谱系（2026-10-04 已交付）恰好都是其下游受益者；
- **叙事对齐**：product-review.md 张力 3 已定稿「虚拟团队（solo orchestration）」——本蓝图就是这句承诺的兑现路径；**多人协作仍是 Non-Goal**（文件黑板 + git 是文件级共享，不是 SaaS 协作功能，边界清楚）；
- **与 dispatch/daemon 的关系**：B/C 均不依赖 daemon（inline-executor 默认路径即可）；多机扩展（B 的 git 语义、C 的远程轮跑）作为后续演进，不进首期。

## 6. 优先级建议

| 阶段 | 内容 | 理由 |
|---|---|---|
| **第一步** | 方向 A 作战室（MVP：KPI 条 + 活动墙 + 成员卡） | 纯组装现有 API/SSE；立即可见价值；为 B/C 提供观察面 |
| **第二步** | 方向 B 文件黑板（MVP：目录级注入 + BOARD.md 约定 + 画布黑板面板） | 引擎改动小（复用 context_md 管线）；同时缓解 D2 的 64KB/单向/易失三痛点 |
| **第三步** | 方向 C 目标环（supervisor + goals 表 + 目标看板） | 新语义，需要 spec；依赖 B 的轮间交接 |
| **持续** | 方向 D 视觉增强随各步渗透 | 非独立立项 |

每步落地走 dagents-patterns 四阶段流程；A/B 建议合并出一份 spec。

## 7. 风险与护栏

| 风险 | 护栏 |
|---|---|
| 持续运行的成本失控 | goal 级预算硬闸（越线停机复用 budget_exceeded 语义）+ Team Room 成本 KPI 常驻可见 |
| 自主循环跑偏（目标漂移/自我验收放水） | 验收标准在 goal 上声明而非每轮自拟；「人批准下一轮」可选闸门（HumanInput 挂起复用）；轮次产出全量留痕（runs + 黑板）可回滚 |
| 黑板并发写坏 | 文件级原子写 + BOARD 分区纪律；MVP 单机单 run 写者为主 |
| 观察面过载（活动墙刷屏） | feed 按节点边界聚合（过程行折叠进节点组，与轨迹台账同粒度），非逐 token |
| 供应链/安全无新增面 | 黑板在既有 cwd 权限模型内（目录级授权已存在）；无新端口、无新外部依赖 |
