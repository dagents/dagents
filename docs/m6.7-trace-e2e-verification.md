# M6.7 — 全链路追溯端到端验证（验证记录）

> 关联 plan: `docs/superpowers/plans/2026-07-08-mvp-implementation.md` §Task M6.7

## 目标

任一任务全链路 trace 可追 —— 选一个任务，从 gateway 追到 daemon/LLM，trace 完整：
`run_id` 串起 gateway → dispatch → daemon → claude adapter → LLM，含 text/tool-use 事件 + usage 落库 + 节点级 span。

## 验收

- ✅ 一个 `run_id` 贯穿每一跳：`runs.id`、`dispatch_tasks.run_id`、`daemon.execute` span 的 `run.id`、`gateway.proxy` span 的 `run.id`、`runs.agent_daemon_calls`、`run_node_spans.run_id` 全部相同。
- ✅ 预测链 OTel traceId 连续：`scheduler.child-run` span 的 traceId 到达 Flowise（gateway→flowise 跳的 `traceparent`），并落在 `run_node_spans.trace_id`。
- ✅ daemon 跳由 `run.id` 关联；"claude adapter → LLM" 跳（fake backend 经 gateway `/api/v1/llm` 打 stub LLM）加入 daemon 的 trace（stub LLM 收到的 `traceparent` 携带 `daemon.execute` 的 traceId）。
- ✅ text + tool-use + tool-result 事件落入 `dispatch_task_events`。
- ✅ usage 落入 `runs.agent_daemon_calls`（per-model tokens）。
- ✅ 节点级 span 落入 `run_node_spans`（≥3 节点，`trace_id` = 预测 traceId，含 token/cost）。

## 测试架构（为什么用真实 `serve()` 而非 `app.request()`）

M6.1 的 `traceparent` 自动注入/抽取依赖 undici（出站）+ `http`（入站）auto-instrumentation。`app.request()` 是进程内调用，**绕过** `http` server instrumentation，无法证明 `traceparent` 真正跨网络跳。本套件用 `@hono/node-server` 的 `serve()` 把 dispatch + gateway 起在临时端口上，stub Flowise + stub LLM/new-api 用真实 `node:http` server，daemon 用真实 `runDaemon`（fake claude backend）。每一跳都是真实 instrumented HTTP 调用 —— 这是 M6.1「同 traceId 贯穿」验收的忠实证明。

```
scheduler.fanOut(childRunId)
  → POST gateway /api/v1/flows/<flowId>/prediction  (x-run-id=childRunId, scheduler.child-run span, run.id=childRunId)
    → gateway.proxy span (run.id=childRunId) + fetch stub Flowise (traceparent 注入)
      → stub Flowise 抽取入站 traceparent，POST gateway /api/v1/dispatch/invoke (x-run-id=childRunId) — 续同一 trace
        → dispatch 入队 dispatch_tasks (run_id=childRunId)，返回 taskId
          → daemon claim（轮询）→ 开 daemon.execute span (run.id=childRunId, task.id)
            → fake claude backend: 产 text + tool-use 事件 + usage；并 fetch gateway /api/v1/llm/* (claude adapter → LLM 跳，加入 daemon trace)
            → daemon reportMessages + completeTask(usage)
          → dispatch 把 usage 追加进 runs.agent_daemon_calls，事件落 dispatch_task_events
      → stub Flowise 轮询 GET /api/v1/dispatch/tasks/:id 至 completed，返回 agentflow 预测响应（含 agentFlowExecutedData）
    → gateway 回显 x-run-id
  → scheduler complete run + ingest run_node_spans (trace_id = 预测 traceId)
```

### 诚实的范围说明 —— 两个 trace 根

daemon 是 pull-based：靠轮询 claim 工作，`daemon.execute` span 只在 task 被 claim 后才开 —— 没有入站请求的 `traceparent` 可抽取来续预测 trace。因此 M6.1 用 `run.id`（`currentRunId()` 读回）把 daemon 跳关联到 run，而非共享 traceId。本套件断言的就是这个诚实契约：

- **预测链**（scheduler → gateway → flowise）共享 ONE traceId（`scheduler.child-run` 的），它也落在 `run_node_spans.trace_id`；gateway 把入站 `traceparent` 原样转发给 Flowise，所以 Flowise 收到的 `traceparent` 集合**包含**该 traceId。
- **gateway.proxy** span 带 `run.id = runId`（gateway 跳的 run-id 关联）。经真实 HTTP 时，Hono 无 OTel 中间件抽取入站 traceparent 进 handler context，所以 `gateway.proxy` 可能自起一个新 trace —— undici 也会注入它的 `traceparent`，故 Flowise 同时收到两个。run 的负载承载关联点是 scheduler 的 traceId（在收到的集合里）+ `run.id` tag（无论 trace 根如何都把 `gateway.proxy` 绑到 run）。
- **daemon 链**（daemon.execute → LLM）共享 ONE traceId（`daemon.execute` 的），stub LLM 收到的 `traceparent` 携带它。
- 单一 `run_id` 把预测 trace 与 daemon trace 绑在一起 —— 正是验收「run_id 串起」所名。
